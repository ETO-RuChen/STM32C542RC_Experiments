# 01 工程全景、HAL2 文件结构与阅读路线

## 1. 先建立正确的心智模型

这个仓库中有五份固件，不是一份“大程序”。以 `02_UART` 为例：

```text
02_UART/
├── 02_UART.ioc2                 硬件/中间件配置源，交给 CubeMX2 打开
└── 02_UART_cmake/               可直接用 CMake 编译的完整导出工程
    ├── main.c                   C 语言入口
    ├── app_uart_demo.c/.h       本实验真正的应用逻辑
    ├── CMakeLists.txt           把生成代码和应用代码组成 ELF
    ├── CMakePresets.json        debug preset 与构建目录约定
    ├── cmake/                   目标芯片、编译选项、源文件清单
    ├── generated/               CubeMX2 生成代码
    ├── stm32c5xx_drivers/       ST HAL/LL 驱动副本
    ├── stm32c5xx_dfp/           STM32C5 Device Family Pack
    ├── arch/cmsis/              Arm CMSIS
    ├── utilities/               basic_stdio 和 C 库系统调用适配
    └── user_modifiable/         启动文件、链接脚本等生成器可维护文件
```

因此，一次完整开发循环是：

```text
.ioc2 修改硬件配置
  -> CubeMX2 重新生成 *_cmake
  -> 检查应用扩展是否仍在
  -> CMake 配置
  -> GCC 编译/链接出 .elf
  -> ST-LINK/SWD 烧录
  -> LED、串口、调试器观察结果
```

### 1.1 这套目录与传统 HAL1 教程有什么不同

网上很多 STM32 教程使用经典 HAL，目录常见为 `Core/Src`、`Core/Inc`，并直接访问全局 `huart2`、`htim6`。本仓库是 STM32CubeMX2 + HAL2 工程，概念相同，但代码组织和 API 已经变化：

| 主题 | 常见 HAL1 工程 | 本仓库 HAL2 工程 |
| --- | --- | --- |
| 应用目录 | `Core/Src`、`Core/Inc` | 工程根的 `main.c`、`app_*.c`，05 另有 `App/` 等目录 |
| 总初始化 | `HAL_Init(); SystemClock_Config(); MX_GPIO_Init();` | `mx_system_init()` 统一调度 |
| UART 句柄 | `UART_HandleTypeDef huart2` | `hal_uart_handle_t`，通过 `mx_usart2_uart_gethandle()` 取得 |
| TIM 句柄 | `TIM_HandleTypeDef htim6` | `hal_tim_handle_t`，通过 `mx_tim6_gethandle()` 取得 |
| 外设初始化 | `MX_USART2_UART_Init(void)` | `mx_usart2_uart_init()` 返回句柄或 `NULL` |
| RCC 控制 | `__HAL_RCC_GPIOA_CLK_ENABLE()` | `HAL_RCC_GPIOA_EnableClock()` |
| EXTI 回调 | 常见 `HAL_GPIO_EXTI_Callback(pin)` | EXTI 句柄 + `HAL_EXTI_RegisterTriggerCallback()` |
| 工程构建 | IDE 工程文件为主 | CMSIS 组件 + CMake 子目标 |

所以阅读 HAL1 示例时，应先提取“要配置什么硬件”和“控制流是什么”，再到本工程的 `mx_*.h` 与 HAL2 头文件中查实际 API，不能直接照抄类型名和函数名。

### 1.2 HAL2 工程目录速查

| 路径 | 内容 | 平时是否应修改 |
| --- | --- | --- |
| `main.c/.h` | 当前固件入口 | 可以改；重新生成后检查是否保留 |
| `app_*.c/.h` | 实验应用逻辑 | 可以直接维护 |
| `generated/hal/` | `mx_system`、RCC、GPIO、UART、TIM、DMA 初始化和 IRQ | 不直接改，通过 `.ioc2` 生成 |
| `generated/utilities/` | basic stdio、syscalls 等组件接线 | 不直接改 |
| `generated/parts/` | 01 的 LED/Button 到实际引脚的映射 | 不直接改 |
| `part_drivers/` | ST 提供的 LED/Button 通用组件 | 通常不改 |
| `stm32c5xx_drivers/hal/` | HAL2 驱动实现 | 原则上不改 |
| `stm32c5xx_drivers/ll/` | 更接近寄存器的 LL 驱动 | 原则上不改 |
| `stm32c5xx_dfp/` | 芯片头文件、寄存器定义、启动/链接模板 | 原则上不改 |
| `arch/cmsis/` | Cortex-M33 核心接口，如 `__WFI()`、NVIC | 原则上不改 |
| `utilities/` | `printf`、newlib syscalls、堆适配 | 通常不改 |
| `user_modifiable/` | 启动文件、链接脚本、RTE 配置和生成基线 | 仅明确需要时修改 |
| `cmake/` | 生成的源文件、组件、编译选项和工具链规则 | 通常不直接改 |
| 根 `CMakeLists.txt` | 组合生成目标并加入自定义应用文件 | 在扩展区维护 |
| `CMakePresets.json` | 构建 preset 和输出目录 | 一般只在更换构建配置时改 |
| `.settings/` | Cube 工具的组件/包状态 | 由工具维护 |
| `.vscode/` | 编辑器与调试配置 | 按开发环境维护 |
| `build/` | CMake cache、目标文件、ELF、map | 可重新生成，不是源码 |

`user_modifiable` 中的 `*.base@2.1.0` 是生成器用于比较或合并的基线副本，不是当前应用入口，不要在里面写业务代码。当前真正参与构建的 `main.c` 位于各 `*_cmake` 根目录，实际启动文件和链接脚本则位于 `user_modifiable/Device/STM32C542RCT6/`。

## 2. 为什么仓库有两百多 MB

每个实验的导出目录都带着一份可独立构建所需的 HAL、LL、CMSIS、设备包和工具代码。好处是单独拷走一个实验也能构建，坏处是五份依赖大量重复。

这些重复文件看起来“冗余”，但当前不应贸然合并，原因是：

- CubeMX2 按工程导出，生成的 `cmake/files.cmake` 和组件版本以相对目录为基础。
- 不同实验启用的 HAL 组件和生成文件不同。
- 合并公共驱动会让以后重新生成任一实验时更容易产生版本漂移。
- 供应商文件的重复主要增加磁盘/Git 体积，不会全部进入固件；链接器的 `--gc-sections` 会剔除未引用函数。

真正应该清理的是应用层的无用逻辑，例如原 `03_TIM` 的空 `App_TimerToggle_Process()` 被主循环无限调用。现在主循环改为 `__WFI()`，现象不变，CPU 不再无意义空转。供应商目录的结构性重复暂时保留。

## 3. 代码所有权分区

### 3.1 可以直接维护的文件

- 每个工程根目录的 `main.c`、`main.h`。
- `app_*.c/.h`。
- 05 的 `App/`、`BSP/`、`Config/`、`Drivers_App/`、`Docs/` 和 `Tools/`。
- 根 `CMakeLists.txt` 中明确标注用于追加源文件、包含目录、宏和链接参数的区域。
- 仓库根 `README.md` 和 `Docs/`。

### 3.2 应通过 CubeMX2 配置改变的文件

- `generated/hal/mx_*.c/.h`：RCC、GPIO、TIM、UART、PWR、NVIC 等。
- `generated/parts/`：01 的按键/LED 对象绑定。
- `generated/utilities/`：basic_stdio 与生成的组件接线。
- `cmake/files.cmake`、`cmake/components.cmake`：生成器维护的源文件/组件集合。

例如要把 USART2 从 115200 改成 921600，正确入口是 `.ioc2`，不是手改 `generated/hal/mx_usart2.c`。手改生成文件短期可能生效，但下次生成会被覆盖，而且 `.ioc2` 会继续显示旧配置。

### 3.3 原则上不要改的第三方文件

- `stm32c5xx_drivers/`
- `stm32c5xx_dfp/`
- `arch/cmsis/`
- `utilities/` 中的 ST 原始组件
- `part_drivers/` 中未明确需要修复的 ST 组件实现

若怀疑 HAL 有问题，应先在应用层封装、通过编译宏覆盖或向上游核对版本。05 的 `app_hal_overrides.h` 和 GNU `--wrap` 就是在不修改生成/HAL 源码的前提下增加参数检查与错误现场采集。

## 4. MCU 从复位到应用的启动链

五个工程的基本启动链相同：

```text
上电/复位
  -> startup_stm32c542xx.c 的 Reset_Handler
  -> 初始化 .data，清零 .bss
  -> SystemInit()
  -> C 运行库初始化
  -> main()
  -> mx_system_init()
  -> 应用模块 Init
  -> while(1) / app_run()
```

`mx_system_init()` 是 CubeMX2 生成的系统级总初始化，典型顺序包括：

1. 前置 hook。
2. MPU/资源隔离基础设置。
3. HAL 初始化和 1 ms timebase。
4. NVIC 优先级分组。
5. I-Cache。
6. RCC 时钟树，将 SYSCLK/HCLK 配为 144 MHz。
7. 电源配置（启用 PWR 的工程）。
8. GPIO、USART、TIM、DMA 等具体外设。
9. 后置 hook。

`main()` 必须检查其返回值。初始化失败后继续访问一个无效 handle，通常只会让错误变得更难定位。

## 5. HAL、LL 和寄存器各自是什么

本仓库同时出现三种硬件访问层：

| 层级 | 示例 | 特点 | 工程中的用途 |
| --- | --- | --- | --- |
| HAL | `HAL_UART_Transmit()` | 参数检查、handle 状态、回调，较易用 | 绝大多数初始化和传输 |
| LL | `LL_TIM_EnableDMAReq_UPDATE()` | 接近寄存器、开销小 | 05 精确控制 DMA request/IRQ |
| CMSIS 寄存器 | `TIM2->CCR1` | 直接读写寄存器 | 05 节点目的地址、诊断与验证 |

这三种方式可以共存，但必须明确“谁拥有状态”。例如 05 最终图由 `dma_graph` 独占 LPDMA1_CH0，因此运行期间不能又调用普通 `HAL_UART_Transmit_DMA()` 抢同一图通道。

## 6. 中断、回调和前台任务

硬件中断不会直接“自动找到你的函数”。完整路径通常是：

```text
外设事件
  -> NVIC 选择 IRQ
  -> generated/hal 中的 Xxx_IRQHandler
  -> HAL_Xxx_IRQHandler(handle)
  -> HAL 回调或已注册回调
  -> 应用只记录事件/更新极少状态
  -> 主循环做打印、格式化和较慢处理
```

本仓库的例子：

- 03：`TIM6_IRQHandler -> HAL_TIM_IRQHandler -> HAL_TIM_UpdateCallback`，回调直接翻转 GPIO。
- 04：`EXTI13_IRQHandler -> HAL_EXTI_IRQHandler -> App_LowPowerDemo_Exti13Callback`，回调只置位和计数。
- 05：EXTI 回调完成去抖后，只更新两个 SRAM 中的 DMA link word，不做串口输出。

中断中不应调用 `HAL_Delay()`、长时间 `printf()`、等待另一个中断完成，或者执行不可控循环。中断越短，系统越容易分析。

## 7. `volatile` 在这里解决什么

`volatile` 告诉编译器：变量可能在当前代码看不到的地方改变，每次使用都要真正读/写内存。本仓库用它连接中断与主循环，或暴露调试诊断：

- 02 的 `g_UartRxFrameReady` 在 UART 回调中置位，在主循环中清零。
- 04 的 `g_WakeupKeyPressed` 和 `g_WakeupCount` 在 EXTI 回调中改变。
- 05 的 `g_app_diagnostics`、`g_dma_graph` 可由 GDB 在故障停机后读取。

`volatile` **不等于线程安全，也不是内存屏障**。05 改 DMA 描述符时仍使用 `__DMB()`/`__DSB()`，并在短临界区里暂时关中断，保证写入顺序与可见性。

## 8. 链接脚本、Flash 和 SRAM

编译只把每个 `.c` 变成 `.o`，链接器再按照 `stm32c542xc_flash.ld` 把内容放进 MCU 地址空间：

- 程序指令和只读字符串通常在 Flash。
- 已初始化的可写变量有 Flash 初值，启动时复制到 SRAM 的 `.data`。
- 零初始化的数组/变量进入 SRAM 的 `.bss`。
- 栈和堆也占用 SRAM。

05 的 PWM LUT 和 DMA 描述符必须在 DMA 可访问的 SRAM 中。尤其 linked-list 的链接地址编码有窗口约束，所以 `dma_graph_build()` 会检查节点首尾地址、4 字节对齐和 64 KB 窗口；这不是普通代码风格检查，而是硬件正确性的组成部分。

## 9. 推荐阅读顺序

第一次读某个工程时按以下顺序：

1. 本仓库根 `README.md` 中的实验表。
2. 对应 `.ioc2` 在 CubeMX2 的 Pinout/Clock/外设配置页面。
3. 工程根 `main.c`，只关心初始化和无限循环。
4. 对应 `app_*.c` 或 05 的 `App/app_main.c`。
5. 应用调用的 BSP/Drivers_App 文件。
6. `generated/hal/mx_system.c`，了解生成器初始化顺序。
7. 对某个 handle 有疑问时再看对应 `mx_uart/tim/gpio.c`。
8. 最后才进入 HAL 驱动实现或芯片参考手册。

这样先看到“程序想做什么”，再追踪“底层如何做到”，不会一开始就被数万行供应商代码淹没。
