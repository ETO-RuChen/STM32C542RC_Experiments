# 02 构建、烧录与操作手册

## 1. 硬件和软件前提

### 1.1 硬件

- NUCLEO-C542RC 开发板。
- 一根能传数据的 USB 线，连接板载 ST-LINK USB 接口。
- 01～05 默认都不需要额外面包板接线。
- 观察 02、04、05 日志时，需要电脑识别 ST-LINK Virtual COM Port。

### 1.2 软件

项目当前生成配置对应：

- STM32CubeMX2/Cube CLI 环境。
- GNU Tools for STM32 14.3.1。
- CMake 3.30 或更高版本。
- Ninja。
- STM32CubeProgrammer，通常通过 `cube programmer` 调用。
- 可选：VS Code、ST 扩展、串口终端和 GDB。

检查命令是否可用：

```powershell
Get-Command cube, cmake, ninja
cube --resolve arm-none-eabi-gcc
cube --resolve programmer
```

注意：某些终端直接执行 `cube --version` 会因为没有找到 STM32Cube 应用目录而失败，但 `cube cmake` 或 `cube --resolve ...` 在正确安装/启动的环境中仍可能可用。若整个 `cube` 环境不可用，使用第 3 节的直接 CMake 方法。

## 2. 连接开发板并确认端口

1. 插入 ST-LINK USB。
2. Windows 设备管理器中应出现 ST-LINK 调试器和一个 COM 端口。
3. PowerShell 可列出串口：

```powershell
Get-CimInstance Win32_SerialPort |
  Select-Object DeviceID, Name, PNPDeviceID
```

4. 记住真实端口，例如 `COM12`。仓库 05 脚本中的 `COM12` 和探头序列号只是原作者机器的已验证值，不是所有电脑都相同。

列出 ST-LINK 探头可使用：

```powershell
cube programmer -l
```

如果命令行列出了多块板，烧录时用 `sn=<序列号>` 指定目标，防止写错设备。

## 3. 编译方法 A：Cube CLI preset

每个 `*_cmake` 目录都有同名的 `CMakePresets.json`。以下以 01 为例：

```powershell
cd D:\Workspace\STM32\STM32CubeMX2\STM32C542RC\STM32C542RC_Experiments
cd .\01_LED_Button\01_LED_Button_cmake

cube cmake --preset debug_GCC_NUCLEO-C542RC
cube cmake --build --preset debug_GCC_NUCLEO-C542RC
```

配置成功会生成 Ninja 构建文件；构建成功会生成：

```text
build/debug_GCC_NUCLEO-C542RC/01_LED_Button.elf
build/debug_GCC_NUCLEO-C542RC/01_LED_Button.map
```

`.elf` 包含可烧录代码和调试符号；`.map` 用于分析每个函数/变量被放到哪里以及占用多少空间。

其他工程只替换目录和产物名：

```powershell
cd .\02_UART\02_UART_cmake
cube cmake --preset debug_GCC_NUCLEO-C542RC
cube cmake --build --preset debug_GCC_NUCLEO-C542RC
```

## 4. 编译方法 B：直接 CMake + ARM GCC

当 `cube cmake` 不能使用时，可以让 CMake 直接调用 STM32Cube 安装的 ARM GCC。先定位实际工具链：

```powershell
$bundleRoot = Join-Path $env:LOCALAPPDATA 'stm32cube\bundles\gnu-tools-for-stm32'
$toolchain = Get-ChildItem -LiteralPath $bundleRoot -Directory |
  Sort-Object Name -Descending |
  Select-Object -First 1
$env:Path = "$(Join-Path $toolchain.FullName 'bin');$env:Path"

arm-none-eabi-gcc --version
```

然后在仓库根目录配置一个全新的构建目录：

```powershell
cmake `
  -S .\01_LED_Button\01_LED_Button_cmake `
  -B .\01_LED_Button\01_LED_Button_cmake\build\local-debug `
  -G Ninja `
  -D 'TOOLCHAIN_FILE=GCC.14.3.1.cmake' `
  -D 'CMAKE_BUILD_TYPE=debug_GCC_NUCLEO-C542RC'

cmake --build .\01_LED_Button\01_LED_Button_cmake\build\local-debug
```

PowerShell 中请保留 `-D 'NAME=value'` 的引号。工具链文件名含多个点，不正确的参数拆分可能让 CMake 误把它解析为 `GCC` 和额外路径。

### 4.1 为什么建议新建构建目录

CMake cache 会保存源码目录的绝对路径。如果工程曾由 `01LED_KEY` 改名为 `01_LED_Button`，或整个仓库被移动，复用旧缓存会出现：

```text
The current CMakeCache.txt directory ... is different than the directory ...
The source ... does not match the source ... used to generate cache.
```

这不是 C 源码错误。最稳妥的做法是换一个从未使用的 `-B` 目录，例如 `build/local-debug`。确认旧目录只有构建产物后也可手动清理，但绝不能删除工程源码目录来解决缓存错误。

## 5. 05 的 APP_PHASE 怎么选

05 通过 CMake cache 变量编译七个递进阶段。同一份源码每次只生成其中一个阶段：

```powershell
cd .\05_DMA_List\05_DMA_List_cmake
cube cmake --preset debug_GCC_NUCLEO-C542RC -DAPP_PHASE=7
cube cmake --build --preset debug_GCC_NUCLEO-C542RC
```

直接 CMake 时：

```powershell
cmake `
  -S . `
  -B .\build\phase7 `
  -G Ninja `
  -D 'TOOLCHAIN_FILE=GCC.14.3.1.cmake' `
  -D 'CMAKE_BUILD_TYPE=debug_GCC_NUCLEO-C542RC' `
  -D 'APP_PHASE=7'
cmake --build .\build\phase7
```

阶段含义：

| 值 | 验证目标 |
| --- | --- |
| 1 | GPIO/EXTI、TIM2 PWM、阻塞 UART 的硬件基线 |
| 2 | UART Direct DMA 和 TIM2_UP Direct DMA |
| 3 | 两个 Timer linked-list 节点 |
| 4 | 单通道 UART/Timer 异构节点 |
| 5 | 正常六节点自主闭环 |
| 6 | 报警双节点自主闭环 |
| 7 | 正常/报警双环和按键运行时改链，默认最终版本 |

切换 `APP_PHASE` 后必须重新运行 configure，不能只运行旧目录的 build 并假设 cache 已改变。

## 6. 烧录 ELF

通用烧录形式：

```powershell
cube programmer `
  -c port=SWD mode=UR reset=HWrst freq=1000 `
  -w .\build\debug_GCC_NUCLEO-C542RC\01_LED_Button.elf `
  -v `
  -rst
```

参数含义：

- `port=SWD`：通过 ST-LINK 的 SWD 接口连接 MCU。
- `mode=UR`：under reset 方式连接，固件异常时也更容易连上。
- `reset=HWrst`：使用硬件复位。
- `freq=1000`：SWD 频率 1000 kHz，兼顾稳定性。
- `-w <elf>`：写入 ELF 中定义的 Flash 段。
- `-v`：写入后回读验证。
- `-rst`：完成后复位运行。

有多块探头时加入：

```powershell
cube programmer -c port=SWD "sn=你的探头序列号" mode=UR reset=HWrst freq=1000 `
  -w .\build\debug_GCC_NUCLEO-C542RC\05_DMA_List.elf -v -rst
```

05 已提供一体化脚本，会先打开串口以捕获启动日志，再烧录、验证、复位并抓取输出：

```powershell
cd .\05_DMA_List\05_DMA_List_cmake
.\Tools\flash_capture.ps1 -Port COM12 -Probe 你的探头序列号 -Seconds 8
```

## 7. 串口终端设置

02、04、05 使用同样参数：

```text
Baud rate: 115200
Data bits: 8
Parity: None
Stop bits: 1
Flow control: None
Line ending for sending: CRLF（02 推荐）
```

同一个 COM 端口同一时间通常只能被一个程序占用。烧录抓取脚本、VS Code 串口监视器、PuTTY、MobaXterm 等不能同时打开同一端口。出现 `Access denied` 时先关闭其他串口工具。

不依赖第三方终端的简单 PowerShell 抓取方式可参考 05 的：

```powershell
.\Tools\capture_serial.ps1 -Port COM12 -Seconds 15
```

## 8. 实验 01 操作与验收

### 步骤

1. 编译并烧录 `01_LED_Button.elf`。
2. 不按 B1，观察 PA5 用户 LED。
3. 按住 B1 超过 30 ms，继续观察。
4. 松开 B1，再观察。

### 预期

- 未按：每 500 ms 翻转一次；亮灭完整周期约 1 s。
- 按住：每 100 ms 翻转一次；亮灭完整周期约 200 ms。
- 松开且通过 30 ms 去抖后恢复慢闪。

### 容易误解的地方

代码中的 `LED_BLINK_NORMAL_MS=500` 是“相邻翻转间隔”，不是完整的亮灭周期。一个周期包含开和关两次翻转，所以周期是 1000 ms。

`BUTTON_DEBOUNCE=0` 不是“没有去抖”。它只关闭 ST part driver 内部依赖 EXTI 的去抖路径；应用层 `app_button_get_debounced_state()` 仍用 10 ms 采样累计出 30 ms 稳定时间。

## 9. 实验 02 操作与验收

### 步骤

1. 打开 115200 8N1 串口终端。
2. 烧录 `02_UART.elf` 或按复位键。
3. 确认看到启动横幅。
4. 输入 `Hello STM32` 并发送 CRLF。
5. 再发送包含空格、数字或短于 64 字节的其他内容。

### 预期

终端输出包含类似：

```text
[UART] RX event: IDLE, length: 13 byte(s)
[UART] RX ASCII: Hello STM32..
[UART] RX HEX  : 48 65 6C 6C 6F 20 53 54 4D 33 32 0D 0A
Echo by DMA: Hello STM32
```

不可打印字节在 ASCII 行显示为 `.`，在 HEX 行显示真实值。一次连续输入超过 64 字节时，接收缓冲区会满并形成一帧，余下数据可能成为下一帧；这不是任意长度协议解析器。

## 10. 实验 03 操作与验收

### 步骤

1. 烧录 `03_TIM.elf`。
2. 观察 PA5 用户 LED 至少 5 秒。
3. 可在 `HAL_TIM_UpdateCallback()` 处打断点，确认 `htim` 是 TIM6 handle。

### 预期

- TIM6 输入时钟 144 MHz。
- `PSC=1439`，计数频率为 `144 MHz / 1440 = 100 kHz`。
- `ARR=49999`，每 `50000 / 100 kHz = 0.5 s` 产生更新事件。
- 每次事件翻转一次 LED，所以完整亮灭周期约 1 s。
- 主循环执行 `WFI`，没有应用任务时等待下一次中断。

调试器单步或断点会改变人眼看到的时序，这是调试暂停造成的，不是定时器配置改变。

## 11. 实验 04 操作与验收

### 步骤

1. 打开串口终端。
2. 烧录 `04_LowPower.elf`。
3. 观察上电日志和 PA5 慢闪。
4. 等待进入 STOP1 的提示和 LED 熄灭。
5. 按下并松开 B1；当前 EXTI 配为 PC13 上升沿，实际板级电平决定触发发生在按下还是松开。
6. 观察唤醒日志和快闪。

### 预期流程

```text
启动/初始化
  -> PA5 慢闪 3 组
  -> 打印将在 3000 ms 后休眠
  -> 等待 3000 ms
  -> 串口排空 100 ms
  -> 暂停 SysTick
  -> 进入 STOP1/WFI
  -> EXTI13 唤醒
  -> 恢复 SysTick 和 RCC
  -> 打印 previous mode、计数和 key_flag
  -> PA5 快闪 6 组
  -> 下一轮
```

如果一进入 STOP1 就立刻醒来，检查是否有其他挂起中断、调试器活动或 EXTI pending。该实验演示控制流，不包含电流测量；要测真实低功耗，还需按板卡手册处理 ST-LINK、跳线和测流路径。

## 12. 实验 05 操作与验收

默认构建 `APP_PHASE=7`。操作摘要：

1. 打开串口并烧录。
2. 正常模式：约 1 s 渐亮、1 s 渐暗、500 ms 暗态，并循环输出 Start/Max/Done。
3. 按 B1：请求进入报警模式，PA5 约 75 ms 亮/75 ms 灭，每组四次，日志为 `[ALARM] Active`。
4. 再按 B1：请求返回正常模式。
5. 切换在 DMA 再次获取分支链接时生效，可能多运行一轮；`desired_mode` 只是软件请求，不是硬件已切换的证明。

## 13. 构建成功不等于哪些事情

编译/链接成功可以证明：

- C 语法和声明一致。
- 所需符号能链接。
- 静态断言成立。
- 当前工具链接受所有编译选项。
- ELF 能落入链接脚本定义的 Flash/SRAM 区域。

它不能单独证明：

- 开发板跳线、电源和 USB 连接正确。
- PC13 的物理有效电平与预期一致。
- 串口 COM 号正确且未被占用。
- STOP1 实际电流达到数据手册指标。
- DMA 运行时改链在所有极端节点边界都满足尚未核对的参考手册规则。

所以每次交付都应把“构建验证”和“硬件验证”分别记录。
